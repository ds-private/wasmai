# Research Prompt (v3): Ultra-Lightweight Code Model Distillation & Heterogeneous Cluster Deployment in 4GB WASM with Rust/Candle
## 1. Primary Research Objective
To establish a robust, production-ready methodology for distilling domain-specific coding intelligence (from large Teacher models) into a family of Student models (small and large). The research must produce a **single Rust/Candle WASM inference binary** that is hardware-agnostic and can be deployed across a **heterogeneous cluster** consisting of:
- **Economy CPU Nodes**: Running small, quantized models (≤3B) for high-volume, low-cost inference.
- **Premium GPU Nodes**: Running large, quantized models (8B–70B) for high-accuracy, complex reasoning tasks.
The system must operate within a **4GB WASM linear memory heap** per instance, while enabling automatic request routing, fallback escalation, and dynamic model selection based on prompt complexity. The target runtimes are **WasmEdge** (with WASI-NN GGUF plugin) and **wasmCloud**.
## 2. Technical Constraints & Boundary Conditions
The research must operate strictly within the following invariant parameters:
- **WASM Linear Memory Ceiling**: ≤ 4.0 GiB per WASM instance (holds KV cache, input/output tensors, and metadata).
- **Model File Size Clarification**: GGUF model weight files (`.gguf`) are **memory-mapped (`mmap`'d) directly into host RAM/VRAM by the WASI-NN plugin**, *not* loaded into the 4GB WASM heap. Therefore, model files can be **larger than 4GB** (e.g., 8B Q4 = ~5GB, 70B Q4 = ~40GB) as long as the physical host has sufficient RAM/VRAM.
- **Framework**: `candle-core` + `candle-transformers` (Rust 1.80+, compiled to `wasm32-wasi`).
- **Quantization Standard**: Must support 4-bit K-quant GGUF formats (e.g., `Q4_K_M`) for all models, with optional `Q5_K_M` or `Q8_0` for high-accuracy GPU nodes if VRAM permits.
- **Runtime Backend**: WasmEdge with WASI-NN GGUF plugin (CPU or CUDA variants).
- **GPU Mode (Optional)**: Must support the CUDA-enabled WASI-NN plugin (`wasmedge-plugin-wasi_nn-cuda`) via the `n_gpu_layers` parameter (0 = CPU-only, 99 = full VRAM offload).
- **Hardware Target**:
  - *CPU Pool*: x86_64/ARM, ≥ 4 GB RAM per instance, SIMD enabled.
  - *GPU Pool*: NVIDIA GPU (L4/A100/H100) with ≥ 8 GB VRAM for 8B models, ≥ 48 GB VRAM for 70B models.
- **Domain Focus**: Initially Python/JavaScript code completion, bug-fixing, and refactoring. Designed to generalize to other proprietary corporate languages.
## 3. Core Research Questions (RQs)
**RQ1: Optimal Model Architecture Selection**
Given the 4GB heap constraint, which base architecture yields the highest **HumanEval pass@1** and **MBPP** scores after 4-bit quantization for the small CPU tier (≤3B)? Compare Qwen2.5-Coder-3B, Stable-Code-3B, and DeepSeek-Coder-1.3B. Quantify the performance-per-byte and performance-per-watt trade-off.
**RQ2: LoRA Adapter Stability & Multi-Tenancy**
How does the application of a LoRA adapter (trained externally on FP16) affect the deterministic inference behavior of a quantized GGUF model in WASM? What is the maximum safe LoRA rank (`r=8` vs `r=16`) to keep total heap usage <3.5 GB? Can multiple LoRA adapters (for different companies/domains) be hot-swapped without reloading the base model?
**RQ3: Synthetic Distillation Fidelity for "Corporate Vernacular"**
What is the minimum synthetic dataset size (generated by a large Teacher API) required to successfully distill a specific company's internal coding style into the 3B (CPU) and 8B (GPU) models without catastrophic forgetting? Investigate DPO vs. SFT for distillation efficiency.
**RQ4: WASM Heap Pressure under GPU Offload & Model Size Scaling**
How does varying the `n_gpu_layers` parameter and model size (3B vs 8B vs 70B) affect **WASM linear memory consumption** versus **host VRAM consumption**? When weights are offloaded to VRAM, does the WASM heap shrink proportionally, or does it retain a fixed metadata overhead? What is the minimum heap usage achievable with full offload (allowing larger KV caches for longer contexts)?
**RQ5: Cross-Mode Performance & Power Trade-offs**
What is the tokens/second throughput, latency (p95), and energy consumption (watts) differential between CPU-only, partial offload, and full offload modes? At what `n_gpu_layers` threshold does the GPU mode become net-positive in latency, and is there a "penalty zone" where PCIe transfer overhead degrades performance?
**RQ6: Graceful Degradation & Auto-Detection**
Can the Rust/WASM module programmatically detect the presence of the CUDA plugin and available VRAM, and fall back to CPU-only without restarting the WASM instance if GPU resources are exhausted or unavailable?
**RQ7: Heterogeneous Cluster Orchestration & Intelligent Routing [NEW]**
Can the same Rust/WASM inference module be configured via environment variables (`MODEL_PATH`, `N_GPU_LAYERS`) to seamlessly operate on CPU-only edge nodes (for small, economical models) and GPU-accelerated cloud nodes (for large, accurate models) without code changes?
- *Sub-question 7.1*: Design a lightweight routing proxy (e.g., Envoy, wasmCloud lattice, or custom Rust router) that classifies incoming coding requests by complexity (token length, AST depth, presence of keywords like "refactor" or "debug") and routes them to the appropriate node pool.
- *Sub-question 7.2*: Measure the Total Cost of Ownership (TCO) per 1M tokens for the hybrid setup (CPU small-model + GPU large-model) vs. a purely GPU-based cluster. What is the cost-savings percentage for a typical enterprise workload (80% simple completions, 20% complex refactors)?
- *Sub-question 7.3*: Implement a "fallback escalation" pattern—if the small CPU model produces a low-confidence output (below a logit/softmax probability threshold), the request is automatically escalated and re-run on the GPU large model for higher accuracy. Quantify the accuracy improvement and latency penalty of this round-trip.
## 4. Proposed Methodology & Technical Pipeline
- **Phase 1: Data Curation (The Distillation Pipeline)**
  - Scrape company repositories (removing PII/secrets).
  - Use a Teacher API (e.g., DeepSeek-V3.2 or Qwen3-Coder-480B) to generate 50k–100k instruction-response pairs covering: *Refactoring, Documentation Generation, Unit Test Writing, and Bug Localization*.
  - Filter via static analysis (linters, AST validators) to ensure syntactical correctness.
- **Phase 2: Offline Student Fine-Tuning (FP16/QLoRA)**
  - Use Candle's training loop (outside WASM, on a Linux GPU instance).
  - Fine-tune two Student models:
    - *Student-Small*: Qwen2.5-Coder-3B (target: CPU pool).
    - *Student-Large*: Qwen2.5-Coder-7B or DeepSeek-Coder-6.7B (target: GPU pool).
  - Apply QLoRA to the base models before conversion to GGUF.
- **Phase 3: WASM Compilation & Dual-Mode Packaging**
  - Cross-compile the Candle inference engine to `wasm32-wasi`.
  - Implement a configuration struct in Rust that reads `MODEL_PATH`, `N_GPU_LAYERS`, and `CONTEXT_SIZE` from environment variables.
  - Package the `.gguf` files and LoRA `.safetensors` into separate OCI artifacts for each model tier.
  - **Critical Implementation Detail**: The Rust code must attempt to load the CUDA plugin via WASI-NN. If it fails (returns `WASINN_ERR`), it automatically sets `N_GPU_LAYERS=0` and continues on CPU.
- **Phase 4: Profiling Matrix (CPU vs. GPU for both small and large models)**
  - Run evaluations in a Dockerized WasmEdge instance with:
    - *Scenario A*: CPU-only, 3B model (`N_GPU_LAYERS=0`).
    - *Scenario B*: Full GPU offload, 3B model (`N_GPU_LAYERS=99`).
    - *Scenario C*: CPU-only, 8B model (testing if host RAM permits).
    - *Scenario D*: Full GPU offload, 8B model.
  - Measure heap usage via `wasmedge` runtime stats, VRAM usage via `nvidia-smi`, and latency via custom Rust timers.
- **Phase 5: Cluster Orchestration & Router Implementation [NEW]**
  - Deploy a wasmCloud lattice or Kubernetes cluster with two node pools:
    - *Pool-CPU*: t3.xlarge instances (4 vCPU, 16 GB RAM).
    - *Pool-GPU*: g4dn.xlarge instances (NVIDIA T4, 16 GB VRAM).
  - Implement a Rust-based sidecar router that:
    1. Parses the incoming prompt.
    2. Computes a complexity score (token count × AST node count).
    3. Routes to CPU pool if score < threshold; otherwise, routes to GPU pool.
    4. Implements escalation: if CPU response confidence < 0.6, re-route to GPU.
  - Measure end-to-end latency including network hops.

## 6. Risk Mitigation & Contingency Plans
- **Risk 1: Model exceeds 4GB WASM heap due to large KV cache.**
  *Mitigation:* Reduce context window from 4096 to 2048 tokens, or implement sliding window attention. For GPU nodes, offloading layers frees heap space for larger caches.
- **Risk 2: CUDA plugin fails during WasmEdge initialization (missing driver/VRAM OOM).**
  *Mitigation:* Implement a robust `try_load_gpu()` function in Rust that wraps the WASI-NN `load` call. On failure, emit a warning log, set `N_GPU_LAYERS=0`, and rebind the inference context to the CPU backend without terminating the Wasm module.
- **Risk 3: PCIe transfer overhead degrades partial-offload performance.**
  *Mitigation:* Force binary behavior: either `N_GPU_LAYERS=0` (CPU only) or `N_GPU_LAYERS=99` (GPU full). Avoid partial offload that causes cache thrashing.
- **Risk 4: Router adds unacceptable latency.**
  *Mitigation:* Implement the router as a lightweight sidecar (Rust + Tokio) that makes the routing decision in < 10ms using cached tokenizers and AST parsers. Pre-warm both models on all nodes to avoid cold-start penalties.
- **Risk 5: CPU model accuracy on complex tasks is too low to justify escalation.**
  *Mitigation:* Use the CPU model's logit entropy as a confidence score. Train a small classifier (a 1-layer MLP) that predicts when the CPU model is likely to fail, based on prompt embeddings, and route to GPU preemptively.
